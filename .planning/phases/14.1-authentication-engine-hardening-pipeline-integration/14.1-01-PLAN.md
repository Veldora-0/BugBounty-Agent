# Plan 14.1-01: Pipeline and Scope Engine Integration

## Objective
Wire the `bb-auth --validate` CLI pipeline end-to-end to coordinate surface discovery, hypothesis generation, and safe execution through an actual bounded request executor without unhandled exceptions. Integrate `framework.scope.engine.ScopeEngine` using its actual `check(target)` API returning `ScopeDecision`, implement deterministic canonical program scope path resolution (`<program_dir>/scope/scope.yaml`), enforce fail-closed scope gating for active runs, and guarantee that dry-run, passive-only, hypothesis-only, and lab modes initiate zero external network requests.

## Read First
- `scripts/bb-auth` (CLI wrapper argument parsing, option forwarding, and execution routing)
- `scripts/bb-auth.cmd` (Windows batch wrapper)
- `framework/authentication/engine.py` (Current `AuthenticationSecurityEngine` orchestration)
- `framework/authentication/policy.py` (Current `AuthenticationSecurityPolicy` and approval gating)
- `framework/scope/engine.py` (Canonical `ScopeEngine`, `ScopeDecision`, `ScopeStatus`, `check()` method)
- `framework/common/config.py` (`init_program_workspace`, `get_program_dir`, `PROGRAM_SUBDIRECTORIES`)
- `framework/validation/request.py` (`ControlledRequest`, `ControlledResponse`, `SafeRedirectHandler`)
- `framework/validation/engine.py` (`SecurityValidationEngine` anti-SSRF IP validation, bounded request dispatcher)

## Context
The brownfield audit revealed three architectural gaps in authentication pipeline initialization:
1. `bb-auth --validate` only formulated a validation plan or summary rather than executing actual hypothesis processing and differential tests through a real request executor.
2. Scope checks did not use the actual `ScopeEngine.check(target)` method and returned types (`ScopeDecision`, `ScopeStatus.IN_SCOPE`), and attempted to look up `scope.yaml` in non-canonical locations rather than the initialized program scope path `<program_dir>/scope/scope.yaml`.
3. Active runs lacked fail-closed enforcement when scope was missing, ambiguous, or unresolvable, risking unauthorized network requests.

This plan resolves these gaps by establishing a minimal, safe, bounded internal request executor, wiring canonical scope resolution, and proving end-to-end orchestration in lab mode.

<action>
Integrate `ScopeEngine` directly into `AuthenticationSecurityPolicy` and `AuthenticationSecurityEngine` using the actual API:
1. Resolve the scope configuration file using deterministic path resolution:
   - Priority 1: An explicitly supplied `--scope <path>` CLI argument or constructor parameter.
   - Priority 2: Canonical initialized program scope path: `<program_dir>/scope/scope.yaml` (or `./scope/scope.yaml` if running from within the program directory).
   - Priority 3: Root fallback `./scope.yaml` only if established in the current working directory.
   - Fail Closed: If scope file is missing, malformed, ambiguous, or cannot be resolved, active validation MUST fail closed immediately: raise `ScopeError` or exit with code 1 without initiating any socket or HTTP traffic.
   - Cross-Program Isolation: Never silently fall back to a different program's scope directory.
2. For each candidate target endpoint, invoke the real `ScopeEngine.check(target)` method.
3. Allow active testing ONLY when the returned `ScopeDecision.status == ScopeStatus.IN_SCOPE`. If status is `ScopeStatus.OUT_OF_SCOPE` or `ScopeStatus.AMBIGUOUS`, reject the target immediately with the decision reason (`ScopeDecision.reason`).
4. Ensure third-party identity and OAuth providers (e.g., `accounts.google.com`, `github.com/login/oauth`, `*.okta.com`) evaluate strictly through `ScopeEngine.check()` and are rejected unless explicitly declared in `scope.yaml`.
5. Offline lab mode (`--lab`) bypasses external scope checks and operates strictly on local synthetic fixtures.
</action>
<acceptance_criteria>
- `AuthenticationSecurityPolicy` loads `ScopeEngine` using `ScopeEngine.from_file(resolved_scope_path)` with canonical priority: `--scope` > `<program_dir>/scope/scope.yaml` > `./scope/scope.yaml` > `./scope.yaml`.
- Missing or malformed scope causes active validation to fail closed immediately before any network activity.
- Target authorization strictly checks `decision = scope_engine.check(target)` and requires `decision.status == ScopeStatus.IN_SCOPE`.
- Never falls back to an unrelated program's scope directory.
- `ScopeEngine` API is preserved exactly as defined in `framework/scope/engine.py` without adding or modifying scope methods.
</acceptance_criteria>

Implement a minimal, safe, bounded HTTP request executor in `framework/authentication/executor.py` (or integrate directly into `AuthenticationSecurityEngine`) reusing the battle-tested bounded execution pattern from `framework/validation/request.py` and `framework/validation/engine.py`:
1. Use standard library `urllib.request` with `SafeRedirectHandler` that re-validates scope via `ScopeEngine.check()` on every redirect hop (max 5 redirects).
2. Anti-SSRF boundary enforcement: Resolve DNS hostnames and block private, loopback, link-local, carrier-grade NAT, cloud metadata (`169.254.169.254`), and multicast IP addresses prior to dispatch.
3. Strict bounds: Enforce request timeout cap (max 10 seconds), max response body read cap (max 100 KB), rate limiting delay between consecutive requests, and overall request budget per endpoint/program.
4. Mode safety invariants:
   - `dry_run=True`: Log planned requests without dispatching any TCP/HTTP connection.
   - `passive_only=True`: Completely bypass the executor; analyze local state only.
   - `hypotheses=True` (without `--validate`): Synthesize hypotheses only, zero probes.
   - `lab_mode=True`: Route all requests directly to deterministic `LocalAuthenticationSecurityLab` simulated fixtures; zero external socket connections.
5. Evidence integration: All dispatched requests and responses must capture sanitized interaction data through `AuthenticationEvidenceManager`.
</action>
