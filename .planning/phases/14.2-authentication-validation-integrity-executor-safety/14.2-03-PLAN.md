# Plan 14.2-03: Genuine Validation Pipeline & Honest Family Status

## Objective
Rebuild the active validation pipeline to eliminate all fabricated synthetic responses from the real-target execution path. Define genuine, bounded, multi-step test sequences for every operational finding family using permitted requests and actual researcher-controlled identities, sessions, and tokens; report an explicit `UNVALIDATED` or `MISSING_PREREQUISITES` state whenever required test credentials or endpoints are unavailable; cleanly distinguish hypotheses, observations, candidates, and validated findings; and preserve the 3 observation-only families as informational hardening observations without escalating them into unproven vulnerabilities.

## Read First
- `framework/authentication/engine.py` (Current validation execution logic in `validate_hypotheses`)
- `framework/authentication/validators.py` (`SafeAuthenticationValidator` and `AuthenticationFalsePositiveClassifier`)
- `framework/authentication/lab.py` (`LocalAuthenticationSecurityLab` scenarios)
- `framework/authentication/models.py` (`HypothesisValidationStatus`, `AuthenticationFindingFamily`)
- `framework/authentication/identity.py` (`IdentityManager`, `IdentityProfile`)
- `framework/authentication/sessions.py` (`SessionAnalyzer`)

## Context
Inspection of `framework/authentication/engine.py` revealed that during `validate_hypotheses()` on real targets, the engine executed a single anonymous `GET` request and then called validation helpers with hardcoded synthetic values:
- `validate_authentication_bypass`: called with hardcoded `auth_status=200, auth_body='{"user_id": "test", "account": "authorized"}'`.
- `validate_session_invalidation`: called with hardcoded `session_id="sess_test_123"`.
- `validate_session_fixation`: called with hardcoded `session_pre="sess_fixed_id", session_post="sess_fixed_id"`.
- `validate_account_enumeration`: called with hardcoded `invalid_status=404, invalid_body='{"error": "user not found"}'`.
- `validate_reset_token_reuse`: called with hardcoded `first_status=200, first_body="password updated"`.

This produced fabricated validation results on real targets without actually executing the necessary authenticated requests, session rotations, multi-trial enumeration queries, or token replay operations.

This plan removes all synthetic comparison data from the operational path and implements genuine, bounded multi-step verification protocols.

<action>
Implement genuine, bounded test sequences for operational families:
1. `AUTHENTICATION_BYPASS`:
   - Requires both anonymous response and authenticated response.
   - If researcher identity is provided: Send anonymous request, then send authenticated request using researcher credentials; compare responses.
   - If anonymous response returns 200 with protected user data identical to authenticated response, confirm finding.
   - If authenticated identity is NOT provided: Send anonymous request only. If 200 is returned, verify it is not a login form or WAF page. If sensitive data patterns are present, classify as `CANDIDATE` (unverified differential), NOT `VALIDATED`.
2. `SESSION_NOT_INVALIDATED`:
   - Requires researcher session. Send authenticated request -> execute logout endpoint -> re-send request with original session token.
   - If post-logout request returns 200 with sensitive data: Confirm `VALIDATED`.
   - If session context is missing: Mark as `SKIPPED` / `MISSING_PREREQUISITES`.
3. `SESSION_FIXATION`:
   - Requires login endpoint. Request pre-auth session cookie -> submit login request under researcher test credentials -> compare post-auth session cookie to pre-auth cookie.
   - If cookies are identical AND session is authenticated: Confirm `VALIDATED`.
   - If credentials unavailable: Mark as `SKIPPED` / `MISSING_PREREQUISITES`.
4. `ACCOUNT_ENUMERATION`:
   - Requires user input parameter (e.g. `username` or `email`).
   - Execute 3 trials for known test user and 3 trials for non-existent randomized user (`nonexistent_<uuid>@example.local`).
   - Compare status codes, error messages, redirect headers, and response body lengths across trials.
   - Only confirm `VALIDATED` if differential is consistent across all trials. If uniform, mark `REJECTED`.
5. `PRE_AUTH_PRIVILEGE_EXPOSURE`:
   - Requires intermediate/pre-MFA session token.
   - Probe sensitive endpoint using pre-MFA token. If full account access is granted without completing MFA challenge: Confirm `VALIDATED`.
6. `PASSWORD_RESET_TOKEN_REUSE`:
   - Requires approved test reset token. Submit reset token -> attempt replay of same token.
   - If server accepts reuse: Confirm `VALIDATED`.
7. `REFRESH_TOKEN_REUSE`:
   - Submit refresh token to obtain new access token -> attempt replay of used refresh token.
   - If server issues new tokens on replayed refresh token: Confirm `VALIDATED`.
8. `PASSWORD_RESET_STATE_CONFUSION`:
   - Requires multi-step reset workflow. Attempt final password update step with an unverified or state-confused token without completing prior email/challenge verification.
   - If server completes password change without required challenge verification: Confirm `VALIDATED`.
   - If workflow steps or test token unavailable: Mark `SKIPPED` / `MISSING_PREREQUISITES`.
9. `MFA_BYPASS`:
   - Requires MFA-enabled test account. Attempt direct access to post-MFA authenticated dashboard/API while bypassing the secondary OTP verification step.
   - If server grants post-MFA access with primary factor alone: Confirm `VALIDATED`.
   - If MFA-enabled test account unavailable: Mark `SKIPPED` / `MISSING_PREREQUISITES`.
10. `MFA_STATE_CONFUSION`:
   - Requires intermediate challenge sessions. Attempt swapping intermediate state tokens across distinct user sessions or replaying intermediate states out of order.
   - If server confuses user identities or completes factor verification for an unassociated session: Confirm `VALIDATED`.
   - If dual intermediate session context unavailable: Mark `SKIPPED` / `MISSING_PREREQUISITES`.
11. `AUTHENTICATION_STATE_INCONSISTENCY`:
   - Requires observable multi-component or gateway-to-backend boundaries. Probe endpoints with mismatched auth headers/cookies to observe divergence.
   - If components disagree, exposing protected data or disparate user contexts: Confirm `VALIDATED`.
   - If component boundary context unavailable: Mark `SKIPPED` / `MISSING_PREREQUISITES`.
</action>
<acceptance_criteria>
- All 11 operational finding families have explicit, authentic differential test procedures.
- Every operational finding requires authentic differential observations; zero synthetic responses are used.
- Missing credentials, test accounts, or session contexts deterministically produce explicit non-validated states (`SKIPPED`, `UNVALIDATED`, or `CANDIDATE`), never false `VALIDATED` findings.
- Multi-trial account enumeration requires consistent differentials across >= 2 trials before confirmation.
</acceptance_criteria>

## Verification Strategy
- **Differential Logic Tests**:
  - Test `validate_authentication_bypass` with and without authenticated baseline.
  - Test `validate_account_enumeration` across uniform responses (must REJECT) vs genuine differentials (must VALIDATE).
- **Status Classification Tests**:
  - Test that observation-only families always yield `INFORMATIONAL` status.
  - Test that missing credentials produce `SKIPPED` or `CANDIDATE`, never `VALIDATED`.
